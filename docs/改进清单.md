# 项目改进清单与远程访问延迟

更新日期：2026 年 9 月 12 日。以下建议尚未全部实现，不应当作当前功能承诺。

当前默认访问方案已改为 **Tailscale Serve**，不使用 Funnel。电脑和手机必须都连接同一 Tailscale 网络；手机免配置访问不再是当前方案要求。

## 本次已实现

- 文档与 Git 提交说明使用中文的约定写入根目录 AGENTS.md，不改写历史提交。
- 网页与 Expo 客户端可选择思考等级，保留服务商扩展值，按模型支持范围联动，下一轮生效并持久化。
- 网页采用手机聊天布局与桌面侧栏，加入会话搜索、快捷新建、安全 Markdown、复制回复、浅深色外观，以及不打断历史阅读的流式滚动。
- 图标与渲染依赖本地托管；应用外壳离线缓存包含加密与图标依赖，排除账号接口和聊天数据。

## Serve 连接速度与 Funnel 对比

当前通过 Serve 私网访问。若手机与电脑建立点对点直连，有机会减少公共中转延迟；若走中继，仍可能出现绕路、延迟或抖动，不能保证 Serve 一定更快。Funnel 的说明保留为历史方案对比，不代表仍在使用公网入口。

有可能，但不是一启用就必然慢。官方流程是：手机 → Funnel 中转服务器 → 电脑 Tailscale → 本地中继。Funnel 公网访问不是手机直接连接电脑，且官方说明存在不可调整的带宽限制。

如果手机和电脑在国内而实际中转路径跨境，额外路由距离、丢包和拥塞可能增加延迟、抖动。不能仅凭域名、Tailscale 私网 IP 或启用状态确定具体国家；本次没有测到你的手机端连接路径与往返延迟。电脑自己能打开域名也不能代表手机路径，因为电脑可能经 Tailscale 私网访问同一域名。

本项目的等待至少分为两段：手机 ↔ 电脑中继，以及电脑 ↔ 模型服务商。若审批、连接、会话列表很快，只有模型迟迟不回复，应优先检查模型端。更换 Funnel 入口不一定改善模型端等待。

## 如何判断慢在哪里

1. 在电脑重复访问 http://127.0.0.1:4123/health，确认本地中继正常；这个接口不等待模型生成。
2. 手机保持 Tailscale 连接，在移动网络和 WiFi 下分别访问实际 Serve 地址的 /health，比较多次完整请求耗时，而不是只看一次首次打开。
3. 同一 WiFi 时，另测电脑局域网地址的 /health 作为参考。Serve 请求若明显更慢而局域网正常，应重点检查点对点连接是否建立，以及中继和运营商路径。
4. 使用同一模型、同一思考等级进行对比，分别记录列表响应、发送确认与首段模型回复耗时，避免将模型计算时间混同于网络延迟。
5. 手机接入 Tailscale 后，在电脑使用 tailscale status 或 tailscale ping 检查手机对应 peer 的 direct/relay 状态；这适用于当前 Serve 私网方案，不等于诊断旧 Funnel 公网路径。

## 优化方案

### 后续若需要手机免配置访问

可以试用与两端运营商连接较好的大陆或邻近地区服务器，使用 frp 反向隧道，加 HTTPS 反向代理。架构为：手机 → 自有 HTTPS 入口 → frp 加密隧道 → 电脑中继。电脑主动连接服务器，手机不用 VPN；入口必须支持 WebSocket，保留 Token、审批、限流和隧道认证。服务器位置只是选型因素，需要试用实测，不能保证标称国内就一定快。

这会增加服务器、域名、证书和运维责任。不要把 Codex app-server 的标准输入输出控制接口公开，也不要在代理日志中记录 Token。若在自有服务器终止 HTTPS，应评估服务器可接触到明文的边界，必要时采用本项目云模式的应用层端到端加密。

Cloudflare Tunnel 也能免路由器端口映射地发布本地服务，但同样经过它的网络入口。不能承诺更换后必然比 Funnel 快或一定避免跨境，需要用相同网络与时间段比较。

### 当前方案：手机开启 Tailscale 与 Serve

默认使用 Serve 私网访问；两端成功建立点对点直连时有机会减少公共中转路径，无法直连时仍可能走中继。电脑运行 tailscale serve --bg 4123，手机加入同一网络并保持连接，不启用 Funnel。

### 项目自身优化

本次已本地打包前端依赖，减少外部 CDN 请求，并按动画帧合并流式渲染。后续可加入静态资源压缩、带版本的缓存、WebSocket 小片段合并、历史分页与增量恢复。这些降低资源和重复传输开销，但不会改变运营商跨境路由，也不能修复模型服务商本身的慢响应。
