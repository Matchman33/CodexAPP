# 长期运行与模型刷新

## 这次故障能确认的事实

提供的日志只记录了旧配置字段警告和会话写入冲突，没有记录 Broker 断开原因、退出码或系统唤醒时间。因此不能仅凭这些日志确定“两天后无法连接”是休眠、断网、代理连接失效还是进程异常退出。本次检查时，本机面板显示 Broker 与 Codex 均已连接，防睡眠状态正常。

代码中确认存在三个恢复缺口：Agent 没有主动探测静默失效的云端连接；登录请求没有超时；启动器没有在进程异常退出后自动重启。Codex 子进程的初始化也缺少超时，退出后等待中的 RPC 不能立即收到失败。这些缺口已补齐。

`already has an active writer` 表示该会话已有其他写入进程，可能来自 Codex 桌面端或另一控制进程。可以继续查看历史，需要发送消息时使用会话占用处理入口。它不等于 Agent 与 Broker 断开，不作为重启服务或强制结束外部进程的依据。

`disable_response_storage`、`network_access`、`windows_wsl_setup_acknowledged` 的警告表示当前 Codex 不认识这些字段；它们被忽略，不是网络连接失败的证据。本次没有修改用户的 Codex 配置。

## 恢复策略

| 故障 | 行为 |
|---|---|
| 网络静默丢包、旧 TCP 连接未报告断开 | Agent 每 20 秒发送心跳，15 秒内未收到响应就断开旧连接并重连 |
| Broker 重启、代理断开、网络恢复 | 自动重连，重试间隔从 1 秒逐步增加，最长 15 秒，附加少量随机延迟 |
| 建立连接或认证一直无响应 | WebSocket 建连 10 秒、认证 15 秒超时后重试 |
| 登录服务无响应或限流 | 登录 15 秒超时；限流遵守 `Retry-After`，避免反复登录 |
| Agent、直连中继或 Broker 异常退出 | 使用 `scripts/run.mjs` 启动时，按 1、2、4 秒等间隔拉起，最长 30 秒；持续运行一分钟后清零退避 |
| Agent、直连中继或 Broker 进程卡住 | 本机启动器通过 IPC 每 10 秒探测，持续 60 秒未响应时重新启动；系统长时间挂起后先重新探测 |
| Codex 控制子进程退出 | 拒绝未完成 RPC，自动重新启动本应用的专用子进程 |
| Codex 控制子进程无响应 | 每 30 秒检查一次，连续两次超过 15 秒无响应后回收自己的控制子进程并恢复连接 |
| 主动退出或 Ctrl+C | 停止，不自动重新拉起 |
| 账号被停用、登录被撤销、同设备被替换 | 显示对应原因，需要用户处理，不无限抢占登录或重新连接 |

仅云端网络重连不会中断本机任务。Codex 控制进程退出或被回收时，等待队列暂停，需要核对历史后手动继续；不会自动重发已执行任务。进程崩溃时未持久化的排队消息可能丢失，不能把自动重启等同于任务可靠持久化。已有的网页“重启本项目”仍等待任务结束，并保存待执行队列。

面板 `/api/status` 返回 `lastConnectedAt`、`lastDisconnectAt`、`reconnectCount` 和当前连接状态。控制台记录断开码、心跳超时、重连次数和子进程退出码，后续故障可据此区分网络和进程问题。

## 本机启动

```powershell
npm ci
$env:CODEXAPP_BROKER = "http://你的服务器IP:8787"
npm run start:agent
```

默认只输出控制面板地址，由用户自行打开。希望本次自动打开时：

```powershell
$env:CODEXAPP_OPEN_PANEL = "1"
npm run start:agent
```

Windows 的防睡眠功能阻止自动睡眠，允许屏幕熄灭。用户主动睡眠、休眠、合盖策略、断电或系统关机期间，CPU 与网络可能停止，应用不能在系统未唤醒时恢复远程访问。长期无人值守应接通电源，并在系统电源设置中避免睡眠/休眠，核对合盖行为；真正休眠后要先通过系统或硬件唤醒，程序再自动重连。

防休眠助手启动超过 15 秒未确认时，日志会出现 `helper startup timed out`。项目继续启动，助手按 1、2、4、8 秒等间隔独立自动重试，最长间隔 30 秒，直到成功或服务停止；运行中助手意外退出也会自动恢复。超时意味着防休眠尚未确认生效，不能按已保护状态处理。

网页主界面在防休眠未生效时持续显示提示；设置页及电脑控制面板显示当前状态，控制面板未登录时也可查看。重新连接会恢复最新状态，成功后提示更新为“防休眠已生效”，不会因为项目已经连上就隐藏失败。日志和状态中的 `retryCount`、`nextRetryAt` 用于定位连续失败与下一次尝试时间。停止服务会取消待执行重试，并释放或终止本服务自己的助手，不修改系统电源设置。

上述启动器需要终端/父进程仍在运行；终端被关闭、父进程被终止、系统重启后，需要重新启动，或另行配置 Windows 任务计划/Linux systemd。打包程序和其他桌面启动器若不经过 `scripts/run.mjs`，不具备这里的进程异常重启能力。

## 云端 Broker

已设置 `HOST`、`PORT`、`PUBLIC_URL`、`DB_PATH`、`ADMIN_TOKEN` 等环境变量后：

```bash
cd /你的项目目录
npm ci
npm run start:broker
```

宝塔 Node 项目可将启动文件改为 `/你的项目目录/scripts/run.mjs`，参数填 `broker`，运行目录填项目根目录，环境变量保留。先停止原 Broker，再启动新入口，避免 `EADDRINUSE`。如果已使用带 `Restart=on-failure` 的 systemd，可以继续直接运行 `cloud/broker.mjs`，无需额外叠加启动器。

Agent 掉线只触发它自己的重连，不因为一台电脑离线就重启全部用户共用的 Broker。当前代码修改不会自动部署到公网服务器。

## 模型目录来源

网页设置的刷新按钮直接请求正在运行的 Codex app-server 的 `model/list`，保留分页、隐藏模型过滤、显示名称、默认模型和思考等级能力。默认模型及默认思考等级通过 `config/read` 获取。请求失败时显示错误并保留上次成功列表；没有能力字段时不根据模型名称臆造支持等级。

项目已移除自实现的模型目录读取器，不再自行解析 `config.toml` 的 `model_catalog_json`、`model_catalog_url` 或 profile，也不读取 `auth.json` 为目录请求附加凭据。目录来源、缓存和配置解释统一交给 Codex，自定义模型 ID 仍可手动填写。刷新只重新请求 Codex 接口，不能保证强制清除 Codex 内部目录缓存；修改服务认证、provider 或目录配置后是否需要重启，以 Codex 自身行为为准。

每次实际启动或重连 Codex 时，直连中继与云 Agent 的共享启动流程都会打印 `[codex] binary: <实际可执行文件路径>`。桌面端更新后可通过该日志检查哈希目录是否变化；日志记录实际解析结果，不将自动定位路径写回项目配置。

## 更新与验证

更新电脑端代码后重启 Agent/中继，使模型接口和路径日志改动生效。网页包含生成图片缩略图及路径识别更新：网页托管端需同步代码并运行 `npm run build:web`，随后刷新页面。仅在网页由 Broker 托管时需要同步更新其网页文件；图片仍经原有连接传输，无需新增公网下载端口。

日常验证限定本次受影响范围：Codex 模型列表和能力、启动及更新后重连路径日志、共享会话调用方、图片路径登记与隐藏目录边界、生成图片缩略图和原有附件预览/下载流程。长期待机和全量浏览器验收不属于本次修改的日常验证范围。
